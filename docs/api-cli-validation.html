XML validation from the command line

Well-formedness check and XSD validation with curl, and how to keep the error report.

Überblick

Der Online XSD Viewer stellt seine Funktionen als HTTP-API unter https://www.xsd-viewer.online/api/ bereit. Alles, was die Web-Oberfläche kann, geht daher auch mit curl oder aus jedem Skript heraus – ohne Browser, ohne Login.

Die Validierung läuft in zwei Schritten:

  1. Das XSD (einzelne Datei, Zip-Paket oder URL) hochladen. Die Antwort enthält eine schema_id.
  2. Das XML gegen diese schema_id validieren. Die Antwort ist der vollständige Fehlerreport als JSON.

Die Prüfung umfasst automatisch beides: zuerst die Wohlgeformtheit (ist es überhaupt gültiges XML?), dann – falls wohlgeformt – die Schema-Validierung gegen das XSD.

Schritt 1: XSD laden und schema_id holen

Einzelne XSD-Datei

SCHEMA_ID=$(curl -s -F "file=@FundsXML4.xsd" \
  https://www.xsd-viewer.online/api/schema/upload | jq -r .schema_id)

echo "$SCHEMA_ID"

Zip mit mehreren XSD-Dateien (Includes/Imports)

Mit main_filename das Wurzel-Schema innerhalb des Zips angeben:

SCHEMA_ID=$(curl -s -F "file=@schema-bundle.zip" -F "main_filename=Root.xsd" \
  https://www.xsd-viewer.online/api/schema/upload | jq -r .schema_id)

XSD per URL

SCHEMA_ID=$(curl -s -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/schema.xsd"}' \
  https://www.xsd-viewer.online/api/schema/url | jq -r .schema_id)

Ohne jq: Die Antwort ist ein JSON-Objekt {"schema_id": "...", "model": {...}}; das model ist die geparste Schema-Struktur und kann ignoriert werden.

Wichtig: Die schema_id zeigt auf einen serverseitigen Cache und läuft nach 60 Minuten ab (Details unter Limits). Ein 404 schema not found or expired bei der Validierung bedeutet nur: Schritt 1 wiederholen.

Schritt 2: XML validieren

XML-Datei hochladen

curl -s -F "file=@document.xml" \
  https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/upload \
  -o report.json

XML per URL

curl -s -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/document.xml"}' \
  https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/url \
  -o report.json

XML als Text im JSON-Body

jq -Rs '{content: ., filename: "document.xml"}' document.xml \
  | curl -s -H "Content-Type: application/json" -d @- \
    https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/text \
    -o report.json

Der Fehlerreport

Die Validierung antwortet immer mit HTTP 200 – auch bei Fehlern. Das Ergebnis steht im JSON-Body. Genau dieser Body ist der Fehlerreport; einen separaten Download-Endpunkt gibt es nicht, deshalb speichert man ihn direkt mit -o report.json.

{
  "schema_id": "…",
  "is_valid": false,
  "reformatted_xml": "<?xml version=…>\n<Root>\n  …",
  "errors": [
    {
      "line": 4,
      "column": null,
      "message": "Element '{http://example.com/simple}Age': This element is not expected. Expected is ( {http://example.com/simple}LastName ).",
      "severity": "error",
      "kind": "schema-validation",
      "path": "/*/*[2]",
      "type_name": null,
      "domain": "SCHEMASV"
    }
  ]
}
FeldBedeutung
is_validtrue = wohlgeformt und schemakonform. false = mindestens ein Fehler in errors.
reformatted_xmlDas eingereichte XML, hübsch formatiert. Alle Zeilen-/Spaltenangaben beziehen sich auf diesen Text, nicht auf die Originaldatei. Bei nicht wohlgeformtem XML: null.
errors[].kindnot-well-formed – XML-Syntaxfehler, Parser hat abgebrochen (dann genau ein Eintrag, keine Schema-Prüfung).
schema-validation – XML ist wohlgeformt, verletzt aber das XSD.
errors[].line / columnPosition im reformatted_xml. column ist in der Praxis meist null (libxml2 liefert für Schema-Fehler keine Spalte); bei Syntaxfehlern steht die Spalte im Meldungstext.
errors[].messageFehlermeldung des Validators (libxml2), z. B. fehlendes Pflichtelement, falscher Datentyp, Pattern-Verstoß.
errors[].pathPositionsbasierter XPath zum betroffenen Element, z. B. /*/*[2] (= zweites Kind des Wurzelelements); Elementnamen stehen in der message.
errors[].severityfatal, error oder warning.

Nur Wohlgeformtheit prüfen?

Einen eigenen „nur wohlgeformt“-Endpunkt gibt es nicht, aber die Unterscheidung ist eindeutig: Ist is_valid false und der erste Fehler hat kind: "not-well-formed", ist die Datei kein gültiges XML. Alle anderen Fehler setzen Wohlgeformtheit bereits voraus.

jq -r 'if .is_valid then "wohlgeformt + valide"
       elif .errors[0].kind == "not-well-formed" then "NICHT wohlgeformt: " + .errors[0].message
       else "wohlgeformt, aber \(.errors|length) Schema-Fehler" end' report.json

Report weiterverarbeiten und herunterladen

Als JSON speichern (Rohreport)

curl -s -F "file=@document.xml" \
  https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/upload \
  -o report.json

Als lesbare Textdatei

jq -r '.errors[] | "\(.kind)\tL\(.line):\(.column)\t\(.path // "-")\t\(.message)"' \
  report.json > errors.txt

Als CSV

jq -r '["line","column","kind","severity","path","message"],
       (.errors[] | [.line,.column,.kind,.severity,.path,.message]) | @csv' \
  report.json > errors.csv

Formatiertes XML mit passenden Zeilennummern

Damit die Zeilennummern im Report zum XML passen, das man vor sich hat:

jq -r '.reformatted_xml // empty' report.json > document.pretty.xml
jq -r '.errors[] | "\(.line): \(.message)"' report.json

Komplettes Skript für CI / Batch

#!/usr/bin/env bash
set -euo pipefail
API=https://www.xsd-viewer.online/api
XSD=$1; XML=$2

SCHEMA_ID=$(curl -sf -F "file=@$XSD" "$API/schema/upload" | jq -r .schema_id)
curl -sf -F "file=@$XML" "$API/schema/$SCHEMA_ID/validate/upload" -o report.json

if jq -e .is_valid report.json >/dev/null; then
  echo "OK: $XML ist valide"
else
  echo "FEHLER in $XML:" >&2
  jq -r '.errors[] | "  L\(.line):\(.column) [\(.kind)] \(.message)"' report.json >&2
  exit 1
fi

Aufruf: ./validate.sh schema.xsd document.xml. Exit-Code 0 bei valide, 1 bei Fehlern, ≠ 0 auch bei HTTP-Fehlern (durch curl -f).

Mehrere XML-Dateien gegen dasselbe Schema: die schema_id nur einmal holen und in einer Schleife wiederverwenden – das spart Uploads und schont das Rate-Limit.

Beispiele: curl, PowerShell, Python

Alle drei Varianten machen dasselbe: XSD hochladen, XML validieren, Report als report.json speichern und die Fehler ausgeben. Exit-Code 0 = valide, 1 = Fehler.

Getestet am 28.08.2026 gegen die Live-API: alle curl-, jq- und Python-Beispiele (valide, invalide, nicht wohlgeformt, Zip-Bundle, URL-Ladeweg, 404-Neuladen, 413 bei 33 MB). Die PowerShell-Beispiele sind aus der offiziellen Invoke-RestMethod-Dokumentation abgeleitet, konnten aber mangels Windows-Umgebung nicht ausgeführt werden.

curl (Bash, ohne jq)

Wer kein jq hat, kann die schema_id mit sed herausziehen und den Report mit python3 -m json.tool lesbar machen:

API=https://www.xsd-viewer.online/api

SCHEMA_ID=$(curl -sf -F "file=@schema.xsd" "$API/schema/upload" \
            | sed -E 's/.*"schema_id":"([^"]+)".*/\1/')
echo "schema_id: $SCHEMA_ID"                          # Zwischenstand prüfen

curl -sf -F "file=@document.xml" "$API/schema/$SCHEMA_ID/validate/upload" -o report.json

python3 -m json.tool report.json | head -40           # lesbar ausgeben
grep -q '"is_valid":true' report.json && echo VALIDE || { echo INVALID; exit 1; }

PowerShell 7+

Invoke-RestMethod -Form (ab PowerShell 7) baut den Multipart-Upload selbst; die JSON-Antwort kommt direkt als Objekt zurück.

$Api = "https://www.xsd-viewer.online/api"

$schema = Invoke-RestMethod -Method Post -Uri "$Api/schema/upload" `
            -Form @{ file = Get-Item .\schema.xsd }
$schemaId = $schema.schema_id

$report = Invoke-RestMethod -Method Post -Uri "$Api/schema/$schemaId/validate/upload" `
            -Form @{ file = Get-Item .\document.xml }

$report | ConvertTo-Json -Depth 5 | Set-Content report.json -Encoding utf8

if ($report.is_valid) {
    Write-Host "VALIDE" -ForegroundColor Green
} else {
    $report.errors | Format-Table line, column, kind, message -AutoSize
    $report.errors | Select-Object line, column, kind, severity, path, message |
        Export-Csv errors.csv -NoTypeInformation -Encoding utf8
    exit 1
}
Windows PowerShell 5.1: -Form gibt es dort nicht. Entweder curl.exe (seit Windows 10 1803 an Bord, nicht das Alias curl) mit den Bash-Beispielen verwenden, oder auf die JSON-Endpunkte ausweichen: Invoke-RestMethod -Method Post -ContentType "application/json" -Body (@{filename="schema.xsd"; content=(Get-Content schema.xsd -Raw)} | ConvertTo-Json) gegen /api/schema/text bzw. /validate/text.

Python 3 (nur Standardbibliothek)

Ohne Zusatzpakete über die JSON-Endpunkte /schema/text und /validate/text – dann entfällt der Multipart-Aufbau. Bei 404 wird das Schema einmal neu geladen.

#!/usr/bin/env python3
import json, sys, urllib.request, urllib.error
from pathlib import Path

API = "https://www.xsd-viewer.online/api"

def post_json(path, payload):
    req = urllib.request.Request(
        API + path, data=json.dumps(payload).encode(), method="POST",
        headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as r:
        return json.load(r)

def load_schema(xsd: Path) -> str:
    return post_json("/schema/text", {"filename": xsd.name,
                                      "content": xsd.read_text("utf-8")})["schema_id"]

def validate(schema_id: str, xml: Path, xsd: Path) -> dict:
    payload = {"filename": xml.name, "content": xml.read_text("utf-8")}
    try:
        return post_json(f"/schema/{schema_id}/validate/text", payload)
    except urllib.error.HTTPError as e:
        if e.code != 404:
            raise SystemExit(f"HTTP {e.code}: {e.read().decode()}")
        schema_id = load_schema(xsd)          # expired → reload once
        return post_json(f"/schema/{schema_id}/validate/text", payload)

if __name__ == "__main__":
    xsd, xml = Path(sys.argv[1]), Path(sys.argv[2])
    report = validate(load_schema(xsd), xml, xsd)
    Path("report.json").write_text(json.dumps(report, indent=2), "utf-8")
    if report["is_valid"]:
        print("VALIDE")
    else:
        for e in report["errors"]:
            print(f"L{e['line']}:{e['column']} [{e['kind']}] {e['message']}")
        print(f"{len(report['errors'])} Fehler", file=sys.stderr)
        sys.exit(1)

Python 3 mit requests

Mit pip install requests wird der Datei-Upload zum Einzeiler und auch Zip-Bundles lassen sich einfach mitschicken:

import json, sys, requests

API = "https://www.xsd-viewer.online/api"

with open("schema-bundle.zip", "rb") as f:
    r = requests.post(f"{API}/schema/upload", files={"file": f},
                      data={"main_filename": "Root.xsd"}, timeout=60)
r.raise_for_status()
schema_id = r.json()["schema_id"]

with open("document.xml", "rb") as f:
    r = requests.post(f"{API}/schema/{schema_id}/validate/upload",
                      files={"file": f}, timeout=60)
r.raise_for_status()
report = r.json()

with open("report.json", "w", encoding="utf-8") as out:
    json.dump(report, out, indent=2)

print("VALIDE" if report["is_valid"] else
      "\n".join(f"L{e['line']}: {e['message']}" for e in report["errors"]))
sys.exit(0 if report["is_valid"] else 1)

Mehrere Dateien: die Funktion in einer Schleife über *.xml aufrufen und dabei SCHEMA_ID/schema_id wiederverwenden – wegen des Rate-Limits (30/min) ggf. eine kurze Pause zwischen den Aufrufen einbauen.

Limits: Größe, Timeouts, Cache

Die Werte gelten für die öffentliche Instanz auf www.xsd-viewer.online (Google Cloud Run). Bei einer eigenen Docker-Installation sind sie über Umgebungsvariablen einstellbar (in Klammern).

LimitWertDetails
Upload-Größe (XSD, Zip, XML)32 MBHarte Grenze des Cloud-Run-Loadbalancers; das Backend lehnt darüber mit 413 ab. Gilt pro Request, also auch für den XML-Body bei /validate/text (UTF-8-kodiert). (MAX_UPLOAD_MB, Default 50)
Abruf per URL10 MB · 10 s · 3 RedirectsBei /schema/url und /validate/url: max. 10 MB Antwort, 10 s Verbindungs-/Lese-Timeout, höchstens 3 Weiterleitungen. Nur http/https, keine privaten/lokalen Adressen. Überschreitung → 400. (FETCH_MAX_RESPONSE_MB, FETCH_TIMEOUT_SECONDS, FETCH_MAX_REDIRECTS)
Request-Timeout60 sCloud Run bricht Anfragen nach 60 s ab (HTTP 504). Parsen und Validieren dauern normalerweise deutlich unter 1 s (gemessen: ~0,2 s pro Request für ein kleines Schema); sehr große Schemata mit vielen Includes können mehrere Sekunden brauchen. Beim ersten Request nach Inaktivität kommt ein Kaltstart von 1–3 s hinzu.
Rate-Limit30 Requests / MinutePro Client-IP, für alle schreibenden Endpunkte zusammen (/schema/upload|url|text und alle /validate/*). Darüber 429. Bei Batch-Läufen: schema_id wiederverwenden und ggf. sleep 2 zwischen Validierungen.
Gültigkeit der schema_id60 min · 32 EinträgeDer Schema-Cache ist ein In-Memory-LRU pro Server-Instanz: Einträge verfallen 60 min nach dem Laden, und bei mehr als 32 gecachten Schemata fliegt das älteste raus. (SCHEMA_CACHE_TTL_MIN, SCHEMA_CACHE_MAX_ENTRIES)
Instanzen0–5Cloud Run skaliert horizontal. Weil der Cache pro Instanz lebt, kann eine schema_id bei Lastspitzen auf einer anderen Instanz landen und dort 404 liefern – siehe Hinweis unten.
DTD / Entities im XML≤ 32 Deklarationen · ≤ 512 ZeichenAus Sicherheitsgründen werden nur einfache interne <!ENTITY>/<!ATTLIST>-Deklarationen mit literalen Werten akzeptiert; externe Entities, Parameter-Entities und verschachtelte Referenzen führen zu 400. Abhilfe: DOCTYPE entfernen und Entity-Werte inline schreiben.
Robuste Skripte: Da eine schema_id aus drei Gründen ungültig werden kann (TTL, Cache-Verdrängung, andere Instanz), sollte ein Skript auf 404 reagieren, indem es das XSD einmal neu hochlädt und die Validierung wiederholt. Die schema_id ist deterministisch: derselbe Inhalt über denselben Ladeweg ergibt dieselbe ID (Upload und /schema/text liefern für dieselbe Datei die gleiche ID, /schema/url eine andere).
validate() {  # $1 = XML-Datei; nutzt globale $XSD, $SCHEMA_ID
  local code
  code=$(curl -s -o report.json -w '%{http_code}' -F "file=@$1"          "$API/schema/$SCHEMA_ID/validate/upload")
  if [ "$code" = 404 ]; then   # Schema abgelaufen → neu laden, einmal wiederholen
    SCHEMA_ID=$(curl -sf -F "file=@$XSD" "$API/schema/upload" | jq -r .schema_id)
    code=$(curl -s -o report.json -w '%{http_code}' -F "file=@$1"            "$API/schema/$SCHEMA_ID/validate/upload")
  fi
  [ "$code" = 200 ] || { echo "HTTP $code: $(jq -r .detail report.json)" >&2; return 2; }
  jq -e .is_valid report.json >/dev/null
}

Overview

The Online XSD Viewer exposes its features as an HTTP API at https://www.xsd-viewer.online/api/. Everything the web UI does can therefore be driven with curl or from any script – no browser, no login.

Validation is a two-step flow:

  1. Upload the XSD (single file, zip bundle or URL). The response contains a schema_id.
  2. Validate the XML against that schema_id. The response is the complete error report as JSON.

The check covers both stages automatically: first well-formedness (is it valid XML at all?), then – if well-formed – schema validation against the XSD.

Step 1: Load the XSD and get a schema_id

Single XSD file

SCHEMA_ID=$(curl -s -F "file=@FundsXML4.xsd" \
  https://www.xsd-viewer.online/api/schema/upload | jq -r .schema_id)

echo "$SCHEMA_ID"

Zip with several XSD files (includes/imports)

Use main_filename to name the root schema inside the zip:

SCHEMA_ID=$(curl -s -F "file=@schema-bundle.zip" -F "main_filename=Root.xsd" \
  https://www.xsd-viewer.online/api/schema/upload | jq -r .schema_id)

XSD from a URL

SCHEMA_ID=$(curl -s -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/schema.xsd"}' \
  https://www.xsd-viewer.online/api/schema/url | jq -r .schema_id)

Without jq: the response is a JSON object {"schema_id": "...", "model": {...}}; model is the parsed schema structure and can be ignored here.

Important: the schema_id points to a server-side cache and expires after 60 minutes (see Limits). A 404 schema not found or expired during validation simply means: repeat step 1.

Step 2: Validate the XML

Upload an XML file

curl -s -F "file=@document.xml" \
  https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/upload \
  -o report.json

XML from a URL

curl -s -H "Content-Type: application/json" \
  -d '{"url":"https://example.com/document.xml"}' \
  https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/url \
  -o report.json

XML as text in the JSON body

jq -Rs '{content: ., filename: "document.xml"}' document.xml \
  | curl -s -H "Content-Type: application/json" -d @- \
    https://www.xsd-viewer.online/api/schema/$SCHEMA_ID/validate/text \
    -o report.json

The error report

Validation always answers with HTTP 200 – even when there are errors. The outcome is in the JSON body. That body is the error report; there is no separate download endpoint, so you save it directly with -o report.json.

{
  "schema_id": "…",
  "is_valid": false,
  "reformatted_xml": "<?xml version=…>\n<Root>\n  …",
  "errors": [
    {
      "line": 4,
      "column": null,
      "message": "Element '{http://example.com/simple}Age': This element is not expected. Expected is ( {http://example.com/simple}LastName ).",
      "severity": "error",
      "kind": "schema-validation",
      "path": "/*/*[2]",
      "type_name": null,
      "domain": "SCHEMASV"
    }
  ]
}
FieldMeaning
is_validtrue = well-formed and schema-conformant. false = at least one entry in errors.
reformatted_xmlThe submitted XML, pretty-printed. All line/column numbers refer to this text, not to the original file. null when the XML is not well-formed.
errors[].kindnot-well-formed – XML syntax error, the parser stopped (exactly one entry, no schema check).
schema-validation – the XML is well-formed but violates the XSD.
errors[].line / columnPosition inside reformatted_xml. column is usually null in practice (libxml2 reports no column for schema errors); for syntax errors the column is part of the message text.
errors[].messageValidator message (libxml2), e.g. missing mandatory element, wrong data type, pattern mismatch.
errors[].pathPositional XPath to the offending element, e.g. /*/*[2] (= second child of the root element); element names are in the message.
errors[].severityfatal, error or warning.

Only checking well-formedness?

There is no dedicated "well-formed only" endpoint, but the distinction is unambiguous: if is_valid is false and the first error has kind: "not-well-formed", the file is not valid XML. Every other error already implies well-formedness.

jq -r 'if .is_valid then "well-formed + valid"
       elif .errors[0].kind == "not-well-formed" then "NOT well-formed: " + .errors[0].message
       else "well-formed, but \(.errors|length) schema error(s)" end' report.json

Complete script for CI / batch use

#!/usr/bin/env bash
set -euo pipefail
API=https://www.xsd-viewer.online/api
XSD=$1; XML=$2

SCHEMA_ID=$(curl -sf -F "file=@$XSD" "$API/schema/upload" | jq -r .schema_id)
curl -sf -F "file=@$XML" "$API/schema/$SCHEMA_ID/validate/upload" -o report.json

if jq -e .is_valid report.json >/dev/null; then
  echo "OK: $XML is valid"
else
  echo "ERRORS in $XML:" >&2
  jq -r '.errors[] | "  L\(.line):\(.column) [\(.kind)] \(.message)"' report.json >&2
  exit 1
fi

Usage: ./validate.sh schema.xsd document.xml. Exit code 0 when valid, 1 on validation errors, non-zero on HTTP errors as well (thanks to curl -f).

Several XML files against the same schema: fetch the schema_id once and reuse it in a loop – fewer uploads, friendlier to the rate limit.

Examples: curl, PowerShell, Python

All three variants do the same thing: upload the XSD, validate the XML, save the report as report.json and print the errors. Exit code 0 = valid, 1 = errors.

Tested on 2026-08-28 against the live API: every curl, jq and Python example (valid, invalid, not well-formed, zip bundle, URL loading, 404 reload, 413 at 33 MB). The PowerShell examples follow the official Invoke-RestMethod documentation but could not be executed for lack of a Windows environment.

Either use curl.exe (bundled since Windows 10 1803 – not the curl alias) with the Bash examples, or fall back to the JSON endpoints: Invoke-RestMethod -Method Post -ContentType "application/json" -Body (@{filename="schema.xsd"; content=(Get-Content schema.xsd -Raw)} | ConvertTo-Json) against /api/schema/text and /validate/text.

Python 3 (standard library only)

No extra packages, using the JSON endpoints /schema/text and /validate/text – that avoids building multipart bodies. On 404 the schema is reloaded once.

#!/usr/bin/env python3
import json, sys, urllib.request, urllib.error
from pathlib import Path

API = "https://www.xsd-viewer.online/api"

def post_json(path, payload):
    req = urllib.request.Request(
        API + path, data=json.dumps(payload).encode(), method="POST",
        headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=60) as r:
        return json.load(r)

def load_schema(xsd: Path) -> str:
    return post_json("/schema/text", {"filename": xsd.name,
                                      "content": xsd.read_text("utf-8")})["schema_id"]

def validate(schema_id: str, xml: Path, xsd: Path) -> dict:
    payload = {"filename": xml.name, "content": xml.read_text("utf-8")}
    try:
        return post_json(f"/schema/{schema_id}/validate/text", payload)
    except urllib.error.HTTPError as e:
        if e.code != 404:
            raise SystemExit(f"HTTP {e.code}: {e.read().decode()}")
        schema_id = load_schema(xsd)          # expired → reload once
        return post_json(f"/schema/{schema_id}/validate/text", payload)

if __name__ == "__main__":
    xsd, xml = Path(sys.argv[1]), Path(sys.argv[2])
    report = validate(load_schema(xsd), xml, xsd)
    Path("report.json").write_text(json.dumps(report, indent=2), "utf-8")
    if report["is_valid"]:
        print("VALID")
    else:
        for e in report["errors"]:
            print(f"L{e['line']}:{e['column']} [{e['kind']}] {e['message']}")
        print(f"{len(report['errors'])} error(s)", file=sys.stderr)
        sys.exit(1)

Python 3 with requests

With pip install requests the file upload becomes a one-liner and zip bundles are just as easy:

import json, sys, requests

API = "https://www.xsd-viewer.online/api"

with open("schema-bundle.zip", "rb") as f:
    r = requests.post(f"{API}/schema/upload", files={"file": f},
                      data={"main_filename": "Root.xsd"}, timeout=60)
r.raise_for_status()
schema_id = r.json()["schema_id"]

with open("document.xml", "rb") as f:
    r = requests.post(f"{API}/schema/{schema_id}/validate/upload",
                      files={"file": f}, timeout=60)
r.raise_for_status()
report = r.json()

with open("report.json", "w", encoding="utf-8") as out:
    json.dump(report, out, indent=2)

print("VALID" if report["is_valid"] else
      "\n".join(f"L{e['line']}: {e['message']}" for e in report["errors"]))
sys.exit(0 if report["is_valid"] else 1)

Several files: call the function in a loop over *.xml, reusing SCHEMA_ID/schema_id – add a short pause between calls if you approach the rate limit (30/min).

Limits: size, timeouts, cache

These values apply to the public instance at www.xsd-viewer.online (Google Cloud Run). On a self-hosted Docker installation they are configurable via environment variables (in parentheses).

LimitValueDetails
Upload size (XSD, zip, XML)32 MBHard limit of the Cloud Run load balancer; the backend rejects anything larger with 413. Applies per request, so also to the XML body of /validate/text (UTF-8 encoded). (MAX_UPLOAD_MB, default 50)
Fetch by URL10 MB · 10 s · 3 redirectsFor /schema/url and /validate/url: max. 10 MB response, 10 s connect/read timeout, at most 3 redirects. Only http/https, no private/local addresses. Exceeding any of these → 400. (FETCH_MAX_RESPONSE_MB, FETCH_TIMEOUT_SECONDS, FETCH_MAX_REDIRECTS)
Request timeout60 sCloud Run aborts requests after 60 s (HTTP 504). Parsing and validation normally finish well under 1 s (measured: ~0.2 s per request for a small schema); very large schemas with many includes can take several seconds. The first request after a period of inactivity adds a 1–3 s cold start.
Rate limit30 requests / minutePer client IP, shared by all write endpoints (/schema/upload|url|text and every /validate/*). Beyond that: 429. For batch runs, reuse the schema_id and add a sleep 2 between validations if needed.
schema_id lifetime60 min · 32 entriesThe schema cache is an in-memory LRU per server instance: entries expire 60 min after loading, and once more than 32 schemas are cached the oldest is evicted. (SCHEMA_CACHE_TTL_MIN, SCHEMA_CACHE_MAX_ENTRIES)
Instances0–5Cloud Run scales horizontally. Because the cache lives per instance, a schema_id may hit a different instance under load and return 404 there – see the note below.
DTD / entities in the XML≤ 32 declarations · ≤ 512 charsFor security only simple internal <!ENTITY>/<!ATTLIST> declarations with literal values are accepted; external entities, parameter entities and nested references yield 400. Fix: drop the DOCTYPE and inline the entity values.
Robust scripts: since a schema_id can become invalid for three reasons (TTL, cache eviction, different instance), a script should react to 404 by re-uploading the XSD once and retrying the validation. The schema_id is deterministic: the same content via the same loading path yields the same id (upload and /schema/text give the same id for the same file, /schema/url a different one).
validate() {  # $1 = XML file; uses global $XSD, $SCHEMA_ID
  local code
  code=$(curl -s -o report.json -w '%{http_code}' -F "file=@$1"          "$API/schema/$SCHEMA_ID/validate/upload")
  if [ "$code" = 404 ]; then   # schema expired → reload, retry once
    SCHEMA_ID=$(curl -sf -F "file=@$XSD" "$API/schema/upload" | jq -r .schema_id)
    code=$(curl -s -o report.json -w '%{http_code}' -F "file=@$1"            "$API/schema/$SCHEMA_ID/validate/upload")
  fi
  [ "$code" = 200 ] || { echo "HTTP $code: $(jq -r .detail report.json)" >&2; return 2; }
  jq -e .is_valid report.json >/dev/null
}

Error codes and limits

HTTPCauseFix
200Validation ran (result in is_valid)–
400URL rejected (not http/https, private address, > 3 redirects, > 10 MB, > 10 s) or unsafe XML (e.g. external entities)Upload the file instead
404schema_id unknown or expiredRepeat step 1
413File too large (> 32 MB)Reduce / split the file
422XSD could not be compiled into a validator (e.g. missing imports)Upload a complete zip with all imports
